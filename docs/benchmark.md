# 성능 측정

> **측정 조건을 먼저 확정하고, 그 다음에 잰다.**
> 재고 나서 조건을 정하면 유리한 숫자를 고르게 된다. 순서가 곧 정직성이다.
>
> 현재 상태: **프로토콜 확정 · 측정 대기 (M1)**

---

## 1. 측정 프로토콜

### 1.1 하드웨어 고정

| 항목 | 사양 |
|---|---|
| CPU | AMD Ryzen 5 9600X (Zen5, 6C/12T) |
| RAM | DDR5-5600 32GB (16×2, 듀얼채널) |
| SSD | Predator GM7000 1TB (NVMe) |
| OS | Windows 11 |

**측정 시 조건**
- 전원 옵션 **고성능** 고정 (절전 상태에서 재면 클럭이 널뛴다)
- 브라우저·Visual Studio 등 배경 프로그램 종료
- 측정 중 다른 작업 금지
- **CPU 온도·클럭을 함께 기록** — 서멀 스로틀링이 걸리면 뒤 회차가 느려진다

> 학교 PC(5900X / 3080)에서도 재면 좋다. **단, 같은 표에 섞지 않는다.**
> 하드웨어가 다른 수치를 한 표에 두면 비교 자체가 무의미해진다.

### 1.2 소프트웨어 조건

| 항목 | 값 |
|---|---|
| Python | 3.x / opencv-python (버전 기록) |
| C++ | MSVC 2022 / **Release / x64 / `/O2`** |
| OpenCV | 양쪽 동일 버전 |

> ⚠️ **Debug 빌드로 측정하면 무효다.**
> Debug C++은 최적화가 꺼져 있고 반복문 검사가 붙어 실제보다 몇 배 느리다.
> 그 상태로 Python을 이겨도 의미 없고, **Release로 쟀냐는 질문에 무너진다.**

### 1.3 입력 규격

| 항목 | 값 |
|---|---|
| 해상도 | 1920×1080 고정 |
| 채널 | BGR 3채널 |
| 소스 | 동일 이미지 파일 1장 (`samples/`) |
| 프레임 수 | 110회 처리 |
| 워밍업 | **앞 10회 폐기** |
| 유효 표본 | 뒤 100회 |

> **워밍업이 왜 필요한가**
> 첫 실행은 항상 느리다. 코드가 CPU 캐시에 안 올라와 있고,
> 파이썬은 모듈 로드, .NET은 JIT 컴파일이 첫 호출에 발생한다.
> 준비운동 없이 100m 재는 것과 같다.

### 1.4 측정 범위

**포함:** 파이프라인 ③~⑧ (Mat 래핑 ~ 면적 계산)

**제외:**
- 디스크에서 이미지 읽기 (SSD 성능을 재는 게 아니다)
- 화면 출력
- DB 접근

> 순수 연산 구간만 잰다. I/O가 섞이면 언어 비교가 아니라 저장장치 비교가 된다.

### 1.5 기록 방식

- 회차별 소요 시간을 **전부 CSV로 저장** (요약값만 남기지 않는다)
- 보고 지표: **평균 / 중앙값 / 표준편차 / 최소 / 최대 / p95**
- 평균만 적지 않는다. **편차가 큰 것 자체가 정보다** (프레임 튐 = 현장에서 치명적)
- 3회 이상 반복 후 회차 간 재현성 확인

## 2. 비교 대상 (3열 원칙)

| # | 구현 | 역할 |
|---|---|---|
| A | Python 순수 반복문 | 최악 기준선 |
| B | **Python + numpy 벡터화** | **공정한 비교 대상** |
| C | C++ (Release, `/O2`) | 목표 |

> **B를 반드시 포함한다.** A와 C만 비교하면
> "느린 쪽만 골라 비교했다"는 반박이 즉시 성립한다.
> B가 이기는 항목이 나오면 **그대로 적는다.** → `decisions.md` ADR-005
