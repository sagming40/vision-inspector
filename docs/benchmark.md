# 성능 측정

> **측정 조건을 먼저 확정하고, 그 다음에 잰다.**
> 재고 나서 조건을 정하면 유리한 숫자를 고르게 된다. 순서가 곧 정직성이다.
>
> 현재 상태: **M1 측정 완료 · M4(C++) 대기**

---

## 1. 측정 프로토콜

### 1.1 하드웨어 고정

| 항목 | 사양 |
|---|---|
| CPU | AMD Ryzen 5 9600X (Zen5, 6C/12T) |
| RAM | DDR5-5600 32GB (16×2, 듀얼채널) |
| SSD | Predator GM7000 1TB (NVMe) |
| OS | Windows 11 |

**측정 시 조건**
- 전원 옵션 **고성능** 고정 (절전 상태에서 재면 클럭이 널뛴다)
- 브라우저·Visual Studio 등 배경 프로그램 종료
- 측정 중 다른 작업 금지
- **CPU 온도·클럭을 함께 기록** — 서멀 스로틀링이 걸리면 뒤 회차가 느려진다

> 학교 PC(5900X / 3080)에서도 재면 좋다. **단, 같은 표에 섞지 않는다.**
> 하드웨어가 다른 수치를 한 표에 두면 비교 자체가 무의미해진다.

### 1.2 소프트웨어 조건

| 항목 | 값 |
|---|---|
| Python | 3.x / opencv-python (버전 기록) |
| C++ | MSVC 2022 / **Release / x64 / `/O2`** |
| OpenCV | 양쪽 동일 버전 |

> ⚠️ **Debug 빌드로 측정하면 무효다.**
> Debug C++은 최적화가 꺼져 있고 반복문 검사가 붙어 실제보다 몇 배 느리다.
> 그 상태로 Python을 이겨도 의미 없고, **Release로 쟀냐는 질문에 무너진다.**

### 1.3 입력 규격

| 항목 | 값 |
|---|---|
| 해상도 | 1920×1080 고정 |
| 채널 | BGR 3채널 |
| 소스 | 동일 이미지 파일 1장 (`samples/`) |
| 프레임 수 | 110회 처리 |
| 워밍업 | **앞 10회 폐기** |
| 유효 표본 | 뒤 100회 |

> **워밍업이 왜 필요한가**
> 첫 실행은 항상 느리다. 코드가 CPU 캐시에 안 올라와 있고,
> 파이썬은 모듈 로드, .NET은 JIT 컴파일이 첫 호출에 발생한다.
> 준비운동 없이 100m 재는 것과 같다.

### 1.4 측정 범위

**포함:** 파이프라인 ③~⑧ (Mat 래핑 ~ 면적 계산)

**제외:**
- 디스크에서 이미지 읽기 (SSD 성능을 재는 게 아니다)
- 화면 출력
- DB 접근

> 순수 연산 구간만 잰다. I/O가 섞이면 언어 비교가 아니라 저장장치 비교가 된다.

### 1.5 기록 방식

- 회차별 소요 시간을 **전부 CSV로 저장** (요약값만 남기지 않는다)
- 보고 지표: **평균 / 중앙값 / 표준편차 / 최소 / 최대 / p95**
- 평균만 적지 않는다. **편차가 큰 것 자체가 정보다** (프레임 튐 = 현장에서 치명적)
- 3회 이상 반복 후 회차 간 재현성 확인

### 3.3 단계별 분해

> 구간별로 나눠 재야 "⑧번에서 대부분 벌었다"고 말할 수 있다.

|---|---|---|---|---|

| ⑤ 블러 | — | 0.703 ms (fps 1422.61) | | |
| ⑥ 이진화 | — | 0.317 ms (fps 3157.20) | | |
| ⑦ 모폴로지 | — | 1.762 ms (fps 567.64) | | |
| **⑧ 블롭·면적 (커스텀)** | 152.655 ms (fps 6.55) | 2295.805 ms (fps 0.44) | | |
| 경계 통과 오버헤드 | — | — | | |

> ④~⑦은 cv2 표준 함수만 쓰는 구간이라 순수 반복문 버전을 따로 만들지 않았다 (`—`로 표시).
> 순수 반복문으로 다시 짜봤자 "당연히 느린" 숫자 하나 더 느는 것뿐, 비교 논거가 생기지 않는다.

**실제 결과:** ④~⑦은 예상대로 3ms 남짓으로 거의 동일 (가설 H1 확인).
⑧에서 큰 차이가 났다는 것도 예상과 같았으나(가설 H3), **방향이 예상과 반대였다** —
numpy(B)가 순수 반복문(A)보다 **15배 더 느렸다.** 원인은 전파 알고리즘이
매 반복(106회)마다 이미지 전체(207만 픽셀)를 훑는 구조라서, A안의 "필요한 곳만
국소 방문"보다 총 연산량이 더 컸기 때문 (`diagnose_stage8_iterations.py`로 확인).

## 4. 해석

- [x] 가설 H1(OpenCV 구간 차이 없음)은 맞았는가
  → **맞았다.** ④~⑦ 단계 fps가 567~3157 사이로 전부 준수한 수준이고,
    합산해도 3ms 남짓. 같은 OpenCV C++ 코드를 부르는 구간이라
    Python에서 호출했다는 사실 자체는 성능에 거의 영향을 주지 않았다.

- [x] 가설 H3(⑧이 지배적)은 맞았는가
  → **절반만 맞았다.** ⑧번(블롭 검출)이 나머지 전부를 합친 것보다
    압도적으로 무거운 구간이라는 예측은 맞았다 (A안 152ms vs 나머지 합산 3ms).
    하지만 "커스텀 로직이니까 numpy로 벡터화하면 더 빠를 것"이라는
    암묵적 전제는 **틀렸다.** numpy(B)가 순수 반복문(A)보다 15배 느렸다.

- [x] 틀렸다면 어떻게 틀렸는지 그대로 기술
  → 전파 알고리즘(shift + minimum 반복)이 매 반복마다 이미지 전체(207만 픽셀)를
    다시 훑는 구조였다. 결함 덩어리 크기에 따라 106회 반복이 필요했고,
    총 연산량이 A안의 "필요한 곳만 국소 방문"보다 훨씬 컸다
    (`diagnose_stage8_iterations.py`로 반복 횟수 확인).
    벡터화 자체는 빠르지만, **알고리즘의 반복 구조가 벡터화와 안 맞으면
    오히려 손해라는 걸 실측으로 확인.**

- [ ] 경계 통과 오버헤드가 이득을 얼마나 잠식하는가
  → **M4 이후 측정.** C++ DLL이 아직 없어 P/Invoke 경계 자체가 존재하지 않음.

- [ ] 결론: 이 아키텍처는 정당화되는가
  → **잠정 보류.** 현재까지는 "Python만으로는 fps 0.44~6.55 수준이라
    실시간 요구(초당 수십 프레임)에 크게 못 미친다"는 것까지만 확인됨.
    C++ 버전(M4)의 실측치가 나와야 "그래서 C++로 옮긴 게 정당했는가"에
    답할 수 있다.

> **가설이 틀렸다면 그게 더 좋은 재료다.**
> "예상과 달랐고, 원인을 이렇게 분석했다"는
> 예상이 맞았다는 말보다 훨씬 강하다. 실제 엔지니어링이 그렇게 생겼다.
