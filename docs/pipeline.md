# 파이프라인

이미지 한 장이 들어와서 DB 한 행이 되기까지.
**각 단계에서 데이터가 어떤 타입이고 누구 소유인지**를 추적한다.

---

## 전체 흐름

```
 ① 이미지 로드            [C#]   파일 → BitmapSource
 ② 버퍼 추출              [C#]   BitmapSource → byte[]
 ─────────── 경계 A ───────────   P/Invoke (pinning)
 ③ Mat 래핑              [C++]  byte* → cv::Mat  ※복사 없음
 ④ 그레이스케일           [C++]  3채널 → 1채널
 ⑤ 블러                  [C++]  노이즈 제거
 ⑥ 임계값 이진화          [C++]  → 흑백 2값
 ⑦ 모폴로지               [C++]  잡티 제거 / 구멍 메움
 ⑧ 블롭 검출·면적 계산     [C++]  ★ 커스텀 구현 구간
 ─────────── 경계 A ───────────   반환
 ⑨ 결과 표시              [C#]   byte[] → WriteableBitmap
 ⑩ OK / NG 판정          [C#]   면적 > 임계 → NG
 ⑪ 이력 INSERT           [C#]   → MariaDB
 ─────────── 경계 B ───────────   시간축 분리 (오프라인)
 ⑫ 통계 분석          [Python]   SELECT → pandas → matplotlib
```

---

## 단계별 상세

### ① 이미지 로드 `C#`
`BitmapImage` 로 파일을 읽는다.
**주의:** WPF는 기본적으로 `Bgra32` 로 디코딩한다. 채널 순서가 BGRA다.
OpenCV도 BGR이라 운 좋게 맞지만, **우연히 맞는 것에 의존하면 안 된다.**
포맷을 명시적으로 고정한다. (`FormatConvertedBitmap`)

### ② 버퍼 추출 `C#`
`CopyPixels()` 로 `byte[]` 를 뽑는다.

여기서 **stride** 개념이 나온다.
> 비유: 공책의 한 줄이 딱 글자 수만큼만 있는 게 아니라
> 오른쪽에 여백이 조금 남는 것과 같다.
> 메모리는 4바이트 단위로 정렬하는 걸 좋아해서,
> 폭 × 채널수가 4의 배수가 아니면 줄 끝에 패딩이 붙는다.

`stride ≠ width × channels` 인 경우가 실제로 있다.
**stride를 함께 넘기지 않으면 이미지가 사선으로 밀려 보인다.**
이 증상 보면 100% 여기다.

### 경계 A 통과
```
C#   : byte[] data, int width, int height, int stride, int threshold
C++  : unsigned char* data, int width, int height, int stride, int threshold
```
마샬러가 배열을 **pinning** 해서 GC가 못 옮기게 고정한 뒤 주소를 넘긴다.
호출이 끝나면 풀린다. → 상세는 `decisions.md` ADR-006

### ③ Mat 래핑 `C++`
```
cv::Mat img(height, width, CV_8UC4, data, stride);
```
이 생성자는 **메모리를 복사하지 않는다.** 남의 버퍼를 가리키기만 한다.
> 비유: 남의 집 주소를 내 수첩에 적어둔 것. 집을 복제한 게 아니다.

따라서 이 `Mat` 은 **C# 배열을 직접 건드린다.** 원본 보존이 필요하면 명시적으로 `.clone()`.

### ④~⑦ 전처리 `C++`
전부 OpenCV 표준 함수.
→ **이 구간은 Python과 성능 차이가 거의 없다.** (`architecture.md` 가설 H1)
정직하게 인정하고 문서에 남긴다.

### ⑧ 블롭 검출·면적 계산 `C++` ★
**이 프로젝트에서 유일하게 성능 논거가 성립하는 구간.**

`cv::findContours` 로 끝내지 않는다. 최소 하나는 직접 구현한다.
- 이진 이미지 순회하며 연결 요소 라벨링, 또는
- 라벨별 픽셀 수 누적 + 무게중심 계산

Python으로 같은 걸 순수 반복문으로 짜면 **여기서 수십~수백 배 차이가 난다.**
M1에서 Python 버전도 반드시 같은 방식으로 구현해야 비교가 성립한다.

> 공정성 원칙: numpy 벡터화 버전도 함께 측정해서 3열 비교표를 만든다.
> C++에 유리한 조건만 골라 쟀다는 반박을 미리 차단한다.

### ⑨ 결과 표시 `C#`
`WriteableBitmap` 에 `WritePixels()`.
매 프레임 새 `BitmapSource` 를 만들면 GC 압력으로 프레임이 튄다. 재사용한다.

### ⑩ 판정 `C#`
```
최대 결함 면적 ≥ 임계값  →  NG
그 외                    →  OK
```
**판정 기준이 C#에 있는 이유:** 현장에서 바뀌는 값이다. 재컴파일 없이 조절 가능해야 한다.

### ⑪ INSERT `C#`
검사 시각 / 결과 / 결함 수 / 최대 면적 / 사용 파라미터 / 이미지 경로.
**사용한 파라미터를 반드시 함께 저장한다.** 없으면 나중에 이력 재현이 불가능하다.

### ⑫ 분석 `Python`
실시간 경로와 **완전히 분리**. 별도 실행.

## 데이터 복사 지점 (성능 관점)

| 지점 | 복사 발생 | 회피 가능? |
|---|---|---|
| ① → ② | ✅ 발생 | 필요악 |
| ② → ③ | ❌ 없음 | pinning + Mat 래핑 |
| ④~⑦ 사이 | ⚠️ 단계마다 | 출력 버퍼 재사용으로 감소 |
| ⑧ → ⑨ | ✅ 발생 | 필요악 |

> **면접 포인트:** "경계를 넘을 때 이미지를 복사하면 그 비용이
> 성능 이득을 상쇄하지 않나요?" — 실제로 나올 수 있는 질문이다.
> 답: 복사는 왕복 2회로 고정이고, 처리 단계는 그보다 훨씬 무겁다.
> **단, 이건 M4에서 실측으로 증명해야 한다.** 말로만 하면 진다.

## 실패 지점 예상

| 증상 | 의심 |
|---|---|
| 이미지가 사선으로 밀림 | stride 미전달 |
| 색이 이상함 (빨↔파) | BGR/RGB 채널 순서 |
| 첫 실행은 되는데 반복하면 죽음 | 버퍼 수명 / 이중 해제 |
| 이미지 아래쪽만 깨짐 | 버퍼 크기 계산 오류 (`stride × height`) |
| 특정 해상도에서만 깨짐 | 패딩 처리 누락 |
