# 아키텍처

> ⚠️ 이 문서의 성능 관련 서술은 **전부 가설이다.**
> M1·M4 측정이 끝나면 실측치로 교체하고, 가설이 틀렸으면 틀렸다고 적는다.
> 틀린 가설을 지우고 결과만 남기는 건 조작이다.

---

## 1. 왜 레이어를 나눴나

한 언어로 다 하면 이렇게 된다.

| 만약 전부 | 문제 |
|---|---|
| **Python** | 커스텀 픽셀 루프에서 프레임 드랍. GUI 배포도 번거로움 |
| **C++** | UI 만드는 데 시간 다 씀. 통계·그래프는 라이브러리 빈약 |
| **C#** | 픽셀 단위 처리에서 네이티브 대비 손해, unsafe 남발하게 됨 |

각 언어가 **비용이 가장 싼 영역**에만 서게 배치하는 게 이 설계의 전부다.

---

## 2. 레이어별 책임

### 2.1 엔진 — C++ (`VisionCore.dll`)

**한다:**
- 이미지 버퍼를 받아 전처리 (그레이스케일 → 블러 → 엣지/임계값 → 모폴로지)
- 결함 후보 영역 검출, 면적 계산
- 처리 결과 버퍼와 수치를 호출자에게 반환

**안 한다:**
- 파일 읽기/쓰기 — 경로 문자열을 경계 너머로 넘기는 순간 인코딩 지옥이 열린다
- 화면 출력 — `cv::imshow` 금지. UI는 C#의 영역이다
- DB 접근
- **판정 기준 결정** — 임계값은 C#이 정해서 넘긴다. 엔진은 계산만 한다

> **원칙:** 엔진은 상태를 갖지 않는다.
> 같은 입력에 같은 파라미터면 항상 같은 출력이 나와야 한다.
> 그래야 테스트가 가능하고, 그래야 성능 측정이 재현된다.

### 2.2 UI — C# WPF (`VisionApp.exe`)

**한다:**
- 이미지 로드, `byte[]` 변환
- 파라미터 UI (슬라이더 등) → 엔진에 전달
- 결과 이미지·판정 표시
- OK/NG 최종 판정, DB 기록

**안 한다:**
- 픽셀 단위 연산 — 이걸 하는 순간 C++을 쓴 이유가 사라진다
- 통계 분석

### 2.3 분석 — Python (`analysis/`)

**한다:**
- DB에서 이력 조회 → pandas
- 불량률 추이, 시간대별 분포 → matplotlib
- 리포트 생성

**안 한다:**
- 실시간 경로에 개입하지 않는다. **완전히 오프라인이다.**

이게 중요한 이유: 파이썬이 실시간 경로에 끼어 있으면
"결국 파이썬이 병목 아니냐"는 반박이 성립한다. 물리적으로 분리해야 방어된다.

### 2.4 저장 — MariaDB

C#이 쓰고, Python이 읽는다.
**두 언어를 직접 연결하지 않는 게 핵심이다.** DB가 중간에서 완충한다.

## 3. 경계 (Boundary)

이 프로젝트에 경계는 두 개뿐이다. 적을수록 좋다.

### 경계 A — C# ↔ C++ (P/Invoke)

**동기 호출.** C#이 부르면 C++이 계산하고 돌려줄 때까지 기다린다.

넘기는 것:
```
입력  : 이미지 버퍼(byte[]) + 폭 + 높이 + 파라미터(int/double)
출력  : 처리된 버퍼(byte[]) + 결함 수치(구조체 또는 out 파라미터)
```

**규칙:**
- 원시 타입(`int`, `double`, `unsigned char*`)과 고정 크기 구조체만 오간다
- 문자열, `std::vector`, `cv::Mat`, C++ 클래스는 **절대 경계를 넘지 않는다**
- 메모리는 **할당한 쪽이 해제한다.** C#이 준 버퍼를 C++이 free 하지 않는다

> 이 규칙을 어기면 힙이 갈린다. C++ 런타임 힙과 .NET 힙은 다른 창고다.
> A창고에서 꺼낸 물건을 B창고 장부로 반납하면 장부가 깨진다.

### 경계 B — C# ↔ Python (MariaDB 경유)

비동기이자 간접적. 서로의 존재를 모른다.
계약은 **테이블 스키마 하나뿐**이다.

## 4. 성능 가설 (검증 대상)

> 여기 적힌 건 아직 사실이 아니다. M4에서 판정된다.

**가설 H1.** OpenCV 표준 함수만 호출하는 구간은 Python과 C++의 차이가 크지 않다.
→ 근거: `cv2`는 C++ 구현의 바인딩이다. 실제 연산은 같은 코드가 수행한다.

**가설 H2.** 차이는 다음 세 곳에서 발생한다.
1. 프레임당 바인딩 호출 오버헤드 (초당 수십 회 누적)
2. 단계 간 중간 배열 재할당 (C++은 버퍼 재사용 가능)
3. **OpenCV로 대체 불가능한 커스텀 픽셀 로직**

**가설 H3.** H2-3이 지배적이다. 따라서 결함 판정 로직의 일부는
의도적으로 직접 구현한다. (블롭 면적 누적, 커스텀 임계 판정 등)

> **이 설계 판단이 프로젝트 전체에서 가장 중요하다.**
> 전 구간을 OpenCV 함수로만 채우면 성능 비교표는 무의미해지고,
> 프로젝트의 존재 이유도 함께 사라진다. → `decisions.md` ADR-005

## 5. 의도적으로 안 넣은 것

| 뺀 것 | 이유 |
|---|---|
| 실제 산업용 카메라 연동 | 장비 없음. 이미지 파일·웹캠으로 대체하고 인터페이스만 분리해둔다 |
| 멀티스레드 파이프라인 | 단일 스레드 성능을 먼저 정직하게 재야 한다. 최적화는 측정 다음이다 |
| 딥러닝 결함 검출 | 고전 영상처리로 먼저 베이스라인을 만든다. M7 선택 사항 |
| 네트워크 분산 | 단일 PC 범위를 벗어나면 완성을 못 한다 |

**안 넣은 이유를 적어두는 게 넣은 것만큼 중요하다.**
면접에서 "왜 이건 없어요?"에 "시간이 없어서"가 아니라
"우선순위 판단의 결과"로 답할 수 있어야 한다.
