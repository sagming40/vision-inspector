# 설계 결정 기록 (ADR)

> **ADR = Architecture Decision Record**
> 비유하면 **진료 차트**다. "이 약을 처방했다"만 적으면 쓸모없고,
> "증상이 이랬고 / 다른 약도 검토했고 / 이 이유로 이걸 골랐고 / 부작용은 이거다"
> 까지 적어야 나중에 다른 의사가 보고 판단할 수 있다.
>
> **결과보다 대안과 트레이드오프를 적는 게 핵심이다.**
> 면접에서 이기는 문서는 "무엇을 했는가"가 아니라 "무엇을 안 했고 왜인가"다.

**형식:** 맥락 / 결정 / 대안 / 트레이드오프 / 상태

---

## ADR-001 · 세 언어를 쓴다

**날짜** 2026-07 · **상태** 승인

### 맥락
요구사항이 성격상 셋으로 갈린다.
실시간 처리(밀리초) / 대화형 UI(생산성) / 사후 분석(생태계).

### 결정
C++ 엔진 · C# WPF UI · Python 분석.

### 대안
| 안 | 기각 사유 |
|---|---|
| Python 단일 (PyQt) | 커스텀 픽셀 로직에서 프레임 드랍. 배포도 무거움 |
| C++ 단일 (Qt) | UI·통계 개발 비용이 과다. 완주 불가 판단 |
| C# 단일 (unsafe) | 가능은 하나 픽셀 연산에서 손해. C++을 쓸 명분이 사라짐 |

### 트레이드오프
- 얻는 것: 각 영역 최적 도구, 언어 경계 처리 경험
- 잃는 것: 빌드 복잡도, 디버깅 난이도, **경계 자체가 버그 온상**
- 위험: **"언어 자랑용"으로 보이면 역효과.** ADR-005 측정이 방어 근거다

## ADR-002 · C# ↔ C++ 연결에 P/Invoke를 쓴다

**날짜** 2026-07 · **상태** 승인

### 맥락
관리(managed) 코드와 네이티브 코드를 잇는 방법은 여럿이다.

### 결정
P/Invoke (`DllImport`).

### 대안
| 방식 | 장점 | 기각 사유 |
|---|---|---|
| **C++/CLI** | C++ 객체를 그대로 다룸 | Windows 전용 심화, 문법이 이질적. 학습 비용 대비 이득 적음 |
| **COM** | 성숙한 표준 | 등록·인터페이스 정의 부담이 과함 |
| **gRPC / 소켓** | 언어·머신 무관 | 직렬화 + 네트워크 스택 비용. **실시간 요구와 정면 충돌** |
| **파일 IPC** | 가장 단순 | 디스크 I/O가 처리 시간을 압도. 논외 |
| **C++ → exe, 프로세스 호출** | 격리 우수 | 프레임마다 프로세스 생성. 논외 |

### 트레이드오프
- 얻는 것: 함수 호출 수준의 최소 오버헤드, 표준적이고 자료 풍부
- 잃는 것: 원시 타입만 오감. 구조체·문자열은 수동 마샬링
- 위험: 호출 규약·비트수 불일치 시 **컴파일은 되고 런타임에 무너진다**

> 면접에서 자주 나온다: "왜 C++/CLI 안 쓰셨어요?"
> 답: 이 프로젝트의 경계는 함수 4~5개 수준이다. 객체를 통째로 오갈 필요가 없어서
> C++/CLI의 이점이 발생하지 않고, 학습 비용만 남는다.

## ADR-003 · Python 프로토타입을 먼저 만든다

**날짜** 2026-07 · **상태** 승인

### 맥락
C++부터 만들고 나중에 Python과 비교할 수도 있다.

### 결정
M1에서 Python 구현·측정을 **선행**한다.

### 근거
1. 알고리즘 검증이 Python에서 압도적으로 빠르다
2. **먼저 잰 숫자만이 근거다.** 나중에 재면 사후 정당화다
3. 순서 자체가 논리다 — "느려서 옮겼다"와 "옮기고 나서 빠르다고 했다"는 다르다

### 트레이드오프
- 잃는 것: 같은 알고리즘을 두 번 구현하는 시간
- 얻는 것: **프로젝트 존재 이유 그 자체**

## ADR-004 · 호출 규약은 `__stdcall` 로 고정

**날짜** 2026-07 · **상태** 승인

### 맥락
함수 호출 시 인자를 올린 스택을 **누가 치우는가**의 규칙.
C++ 기본은 `__cdecl`, .NET `DllImport` 기본은 `StdCall`. **기본값이 서로 다르다.**

### 결정
양쪽에 명시적으로 `__stdcall` / `CallingConvention.StdCall` 을 못박는다.

### 근거
불일치해도 **컴파일 에러가 안 난다.** 값도 맞게 나온다.
스택만 조금씩 어긋나다가 한참 뒤 무관한 위치에서 터진다.
Debug에선 멀쩡하고 Release에서 죽는 최악의 유형.

> 참고: x64에서는 호출 규약이 사실상 하나로 통일되어 이 문제가 대부분 사라진다.
> 그래도 명시한다 — x86 빌드 가능성과 문서로서의 의도 전달 때문.

### 트레이드오프
- 잃는 것: 매 함수마다 키워드 반복
- 얻는 것: 재현 어려운 버그 클래스 하나를 통째로 제거

## ADR-005 · 결함 판정 로직 일부를 직접 구현한다 ★

**날짜** 2026-07 · **상태** 승인 · **중요도 최상**

### 맥락
**`cv2` 는 OpenCV C++ 구현의 얇은 바인딩이다.**
`cv2.GaussianBlur()` 가 실행하는 코드와
C++ `cv::GaussianBlur()` 가 실행하는 코드는 **같은 기계어다.**

따라서 파이프라인 전체를 OpenCV 표준 함수로만 채우면
**Python과 C++의 성능 차이는 거의 나지 않는다.**
그 상태로 만든 비교표는 근거가 없고, 이 프로젝트의 명분도 무너진다.

### 결정
파이프라인 ⑧단계(블롭 검출·면적 계산)를 **직접 구현한다.**
`cv::findContours` 로 대체하지 않는다.

M1 Python 버전도 **동일 알고리즘**으로 구현하고,
비교표는 **3열**로 만든다.

| 구현 | 성격 |
|---|---|
| Python 순수 반복문 | 최악 기준선 |
| Python + numpy 벡터화 | **공정한 비교 대상** |
| C++ | 목표 |

### 근거
- 2열(순수 Python vs C++)만 제시하면 "느린 쪽 골라 비교했다"는 반박이 즉시 성립한다
- numpy 열을 포함하는 순간 **정직한 비교로 격상된다**
- numpy가 이기는 항목이 나와도 **그대로 적는다.** 유리한 숫자만 남기면 조작이다

### 트레이드오프
- 잃는 것: 구현 시간 증가, 알고리즘을 3번 작성
- 얻는 것: **성능 논거의 유일한 성립 근거**

> 이 ADR이 프로젝트 전체에서 가장 중요하다.
> 이걸 모르고 진행하면 면접 한 질문에 논리 전체가 붕괴한다.

## ADR-006 · 이미지 버퍼는 C#이 소유한다

**날짜** 2026-07 · **상태** 승인

### 맥락
.NET 힙과 C++ 런타임 힙은 **서로 다른 창고이며 장부도 다르다.** 한쪽에서 할당한 메모리를 다른 쪽에서 해제하면 장부가 깨진다.

또한 .NET GC는 메모리를 정리하며 객체를 **이사시킨다.** C++에 주소를 넘긴 뒤 이사가 일어나면 엉뚱한 곳을 쓰게 된다.

### 결정
- 모든 이미지 버퍼는 C#이 할당하고 C#이 해제한다
- C++은 **빌려 쓰기만 한다.** `new` / `malloc` 으로 반환하지 않는다
- 결과도 C#이 미리 준비한 출력 버퍼에 채워 넣는다

### 근거
마샬러가 호출 직전 배열을 **pinning** — 바닥에 못질해 GC가 못 옮기게 한다.
호출이 끝나면 자동으로 풀린다. `byte[]` 같은 단순 타입은 자동 처리된다.

> **핵심:** pinning은 **호출 중에만** 유효하다.
> C++이 포인터를 멤버 변수에 저장해두고 나중에 쓰면 그 시점엔 이미 이사 갔을 수 있다.
> → `architecture.md` "엔진은 상태를 갖지 않는다" 원칙이 여기서 나온다.

### 트레이드오프
- 잃는 것: 호출자가 출력 크기를 미리 알아야 함
- 얻는 것: 메모리 소유권이 한 곳으로 단일화, 누수·이중 해제 원천 차단

### 검증 (M3)

이론이었던 pinning을 실측으로 확인함.

- `byte[] testData = { 0, 100, 255 }` 를 C#에서 생성
- `Invert(testData, testData.Length)` 호출 — C++이 그 주소를 받아 `for` 루프로 직접 반전
- 호출 후 **같은 배열**을 다시 읽음 → `{ 255, 155, 0 }`

원본이 그대로 뒤집혀 있다는 것은, 마샬러가 호출 구간 동안 배열을 고정(pin)해 C++이 진짜 원본 메모리를 건드렸다는 뜻이다. 만약 pinning이 없었다면 GC가 호출 도중 배열을 이동시킬 수 있어 크래시나 정의되지 않은 동작으로 이어졌을 것이다 — 지금은 작은 배열이라 위험 확률이 낮았을 뿐, 설계상 안전한 게 아니라 **아직 터지지 않은 것**에 가깝다는 점을 유의.

## ADR-007 · Add는 값 전달, Invert는 참조(주소) 전달

**날짜** 2026-07 · **상태** 승인

### 맥락
M2의 `Add(int a, int b)`와 M3의 `Invert(unsigned char* data, int length)`는 겉보기엔 둘 다 "C#에서 C++로 데이터를 넘긴다"는 같은 동작처럼 보이지만, 실제로 넘어가는 것의 성격이 다르다.

### 결정
- `Add`: 정수 두 개를 **복사**해서 넘긴다 (값 전달, pass by value)
- `Invert`: 배열의 **시작 주소**를 넘긴다 (참조/포인터 전달, pass by reference)

### 근거
`int a, int b` 같은 원시 값 하나는 복사 비용이 사실상 0에 가깝다. 반면 이미지 픽셀 배열은 수백만 바이트에 달해서, 호출마다 전체를 복사하면 그 복사 비용 자체가 실시간 처리 요구(ADR-001)와 정면 충돌한다.

그래서 큰 데이터는 "값을 복사해서 주고받는 것"이 아니라 "데이터가 있는 위치(주소)만 알려주고, 그 자리에서 직접 읽고 쓰게" 하는 쪽을 택했다.

### 검증
| 함수 | 넘기는 것 | 호출 후 원본 상태 |
|---|---|---|
| `Add(3, 4)` | 정수 값의 복사본 | C# 쪽 원본 변수는 애초에 없음 — 매번 새 값만 돌아옴 |
| `Invert(testData, 3)` | `testData` 배열의 시작 주소 | `{0,100,255}` → `{255,155,0}`, **원본이 직접 바뀜** |

M3에서 실제로 이 표의 두 번째 줄을 실측 확인함.

### 대안
| 방식 | 기각 사유 |
|---|---|
| `Invert`도 값 전달처럼, 결과 배열을 새로 만들어 리턴 | 리턴 시점에 다시 전체 복사가 필요해 배열이 커질수록 비용이 커짐. ADR-006(C#이 버퍼 소유)과도 어긋남 |
| 매번 새 배열 `malloc` 후 반환 | C++ 힙에서 할당한 메모리를 C# 쪽에서 해제해야 하는 소유권 혼선 발생 (ADR-006 참고) |

### 트레이드오프
- 얻는 것: 복사 비용 없이 원본을 직접 수정 → 실시간 처리에 적합
- 잃는 것: 포인터가 유효한 범위(호출 중 pinning 구간)를 벗어나 사용하면
  정의되지 않은 동작으로 이어짐 — 안전성을 프로그래머가 직접 책임져야 함
- 관련: pinning의 구체적 동작은 ADR-006 참고

## 작성 규칙

1. **결정할 때 쓴다.** 나중에 몰아 쓰면 이미 왜곡돼 있다
2. **기각한 대안을 반드시 남긴다.** 이게 ADR의 존재 이유다
3. **번복해도 지우지 않는다.** 상태를 `폐기 — ADR-0XX로 대체` 로 바꾸고 남긴다
   → 판단이 바뀐 기록 자체가 성장의 증거다
4. **가설과 사실을 구분해 표기한다**
